# A BotMaker Studio plugin

Generated by `botmaker-plugin-archetype`. It compiles and its tests pass as it stands.

# Build it

```bash
mvn verify
```

There is no `.gitignore` — Maven's archetype packaging drops the file silently, so it could not be shipped.
Add one before your first commit; `target/` is the whole of the minimum.

# What is in here

- `ExampleApi` — the API your plugin offers a bot. Every `public` method it declares is offered in Studio's
  block palette; `@Hidden` takes one back out. Renaming a method renames its palette entry, because nothing
  lists member names as strings.
- `ExamplePlugin` — the plugin itself: the palette, the one type it owns, and one slot editor chosen by
  the call. Studio finds it through `src/main/resources/META-INF/services/com.botmaker.plugin.api.StudioPlugin`,
  which holds its fully-qualified name. **If you rename or move `ExamplePlugin`, edit that file too** —
  nothing else will tell you.
- `Greeting`, `GreetingType`, `GreetingEditor` — a value a bot can hold, its one declaration (what a new
  one is, and the components the host writes it as), and what it looks like when clicked.
- `ExamplePluginTest` — the palette, the type and its round trip, and the editor's predicate including the
  contexts it must *decline*.

# The three dependencies, and why their scopes differ

- `botmaker-studio-api` is **`provided`** — Studio already has the contract, and a contract class must be
  the *same* `Class` object on both sides of the plugin boundary.
- `botmaker-plugin-toolkit` is **`compile`** — it is resolved onto *your* plugin's classloader, so your
  version is yours and no other plugin's. Studio does not have it. Do not mark it `provided`.
- `javafx-controls` is **`provided`** — you draw into the host's scene graph.

# The versions are `main-SNAPSHOT` unless you said otherwise

That is the tip of each BotMaker repository's main branch, which is right for trying things and wrong for
anything you intend to publish. Change both to released tags in `pom.xml` before you release, and re-run
`mvn verify`.

# Three rules an editor must keep

1. **A widget takes a `ValueContext` and gets everything else from it** — theming, dialogs, capture and the
   project's paths are all on `ctx.services()`. If you need something that is not there, the *contract* is
   missing it; say so rather than routing around it.
2. **Nothing throws while building a node.** A stored value is text a user may have typed anything into, or
   that a newer version of your plugin wrote. An editor that throws in its constructor leaves a row of the
   Parameters window empty with no explanation, which reads as the host being broken.
3. **Building an editor never writes** — not even to normalise what is already there. A project opened and
   closed must come back byte-identical.

# Next

- Declare each type you own once, in `buildTypes()`. The class is the identity: a bot holds it as Java, and
  a project opened without your plugin shows that Java read-only rather than losing it. Keep
  `build(components(fresh()))` giving the same components back — `botmaker plugin validate` checks it.
- A type's own editor is `PluginType.editor`. Add a `SlotEditor` only when the **call** decides what a value
  means (`SlotEditor.forCall(...)`) — a Steam app id and a window title are both `String`.
- Read the toolkit's Javadoc. Every widget's doc says which mistake it exists to prevent.
